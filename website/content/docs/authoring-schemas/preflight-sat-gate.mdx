Before Veritas touches a GPU or spends a token, it checks whether the constraints can be satisfied at
all. That is the whole promise of the gate: **0 LLM tokens**, pure local computation, and a verdict you
can put in CI.

<StatGrid>
  <Stat value="0" label="tokens spent" tone="pass" />
  <Stat value="SAT" label="checked witness" tone="cobalt" />
  <Stat value="UNKNOWN" label="never a guess" />
  <Stat value="2" label="exit codes that matter" />
</StatGrid>

## Why it matters

Six weights capped at 15% cannot sum to 100%. Without pre-flight you would pay for every token of a
decode that can never succeed:

<CodeBlock language="python" title="contradiction by arithmetic" code={`require(sum(p.weights.values()) == 1.0)                     # 100% invested
require(forall(p.weights.values(), lambda w: w <= 0.15))    # 6 x 0.15 = 0.90 < 1.0

# InfeasibleSpecError: Spec portfolio is infeasible at pre-flight`} copyable />

## Where the verdict comes from

Compilation and pre-flight happen when a `@verified_schema` module is imported, not when you first call
`verify`. The check runs the pipeline in this order:

1. transpile the decorated function into a `VirSpec` and build the dependency graph;
2. contract numeric domains with the HC4/interval layer;
3. check container feasibility for dynamic maps and residual sums;
4. solve the exact rational linear relaxation, including strict-bound refutation;
5. synthesise and *check* string/format witnesses;
6. only then — if a concrete witness survived — report `SAT`.

A step that cannot decide returns `UNKNOWN`. It never turns "unsupported" into "true".

## `schema.preflight` and `run_preflight(spec)`

<CodeBlock language="python" title="reading the result" code={`from portfolio_spec import portfolio          # pre-flight already ran at import
from veritas import run_preflight

report = portfolio.preflight                  # PreflightResult, computed once
print(report.status)                          # 'SAT' | 'UNKNOWN' | 'UNSAT'
print(report.is_sat)                          # True only for a checked witness
print(report.witness)                         # the witness that was checked, when there is one
print(report.details)                         # why it is UNKNOWN, in English

fresh = run_preflight(portfolio.spec)         # re-run against the compiled spec
assert fresh.status == report.status`} copyable />

<Callout variant="warn" title="UNKNOWN is not a failure">
`UNKNOWN` means pre-flight could not construct a witness — the usual cause is a dynamic `dict`
container, whose key set is not known until values arrive. The spec can still be perfectly good: `verify`
decides every concrete instance, and generation has its own masks. Treat `UNKNOWN` as "not proved here",
not as "broken".
</Callout>

<CodeBlock language="bash" title="a contradiction: exit 2, no report" code={`$ veritas check-spec window_spec.py
error: InfeasibleSpecError: Spec window is infeasible at pre-flight
# exit 2`} copyable />

`--json` returns one object per schema with `fields`, `derived`, `requires`, `derives`, `containers`,
`zero_dof_rules`, `preflight: {status, conflicts, relaxation}` and `digest` — parse `preflight.status`
rather than the exit code when you need to distinguish `UNKNOWN` from `UNSAT`.

<Callout variant="info" title="There is no --strict on check-spec">
Only `doctor` has `--strict`. `check-spec` exits 0 for `SAT`, 1 for `UNKNOWN`/`UNSAT`, and 2 when the
module raises at import.
</Callout>

## Errors

### `InfeasibleSpecError`

Raised at import when the spec cannot be satisfied. It carries the indices that conflict and, when the
cause is understood, a structured relaxation hint:

<CodeBlock language="python" code={`import veritas as vt

try:
    from window_spec import window        # end >= 8 and end <= 3
except vt.InfeasibleSpecError as exc:
    print(exc)                            # Spec window is infeasible at pre-flight
    print(exc.conflicts)                  # [0, 1]
    print(exc.relaxation["details"])
    # ['exact rational linear relaxation is infeasible',
    #  "'end' has lower bound 8 above upper bound 3"]
    print(exc.relaxation["hints"])
    # ['constraint #0 \`end >= 8\` participates in a conflict', ...]
    print(exc.relaxation["suggestion"])
    # 'Relax a listed constraint or a field bound.'`} copyable />

It subclasses `ValueError`, so `except ValueError` also catches it — and so does `except Exception`,
which is why the specific class is worth naming.

### `CircularDerivationError`

A `derive` chain that feeds back into itself. The exception is plain: one message, no attributes.

<CodeBlock language="python" code={`try:
    from circular_spec import circular
except vt.CircularDerivationError as exc:
    print(exc)     # Cycle detected in vt.derive dependency graph`} copyable />

<Callout variant="warn" title="No StrictBoundRefutation, no derived_fields">
Earlier drafts of this page described a `StrictBoundRefutation` class and read `report.sat`,
`report.derived_fields` and `report.bounds`. None of those exist: strict-bound refutation is a step
inside pre-flight that contributes to `status` and `details`, and the report fields are the ones in the
table above.
</Callout>

## Complete example

<CodeBlock language="python" title="pre-flight before decode" code={`import veritas as vt
from pydantic import BaseModel, Field

RETURNS = {"AAPL": 0.12, "MSFT": 0.10, "NVDA": 0.15}

class Portfolio(BaseModel):
    weights: dict
    expected_return: float

@vt.verified_schema()
def portfolio(p: Portfolio):
    vt.require(vt.keys_subset(p.weights, {"AAPL", "MSFT", "NVDA"}))
    vt.require(vt.sum(p.weights.values()) == 1.0, tol=1e-6)
    vt.require(vt.forall(p.weights.values(), lambda w: (0.05 <= w) & (w <= 0.60)))
    vt.derive(p.expected_return == vt.dot(p.weights, RETURNS), tol=1e-5)
    vt.require(p.expected_return >= 0.10)

print(portfolio.preflight.status)   # UNKNOWN for a dynamic map, never a guessed SAT
print(portfolio.preflight.details)`} copyable />
