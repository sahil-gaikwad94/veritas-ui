**Veritas turns plausible LLM output into checked output.** You write a Pydantic model and a few
constraint statements; Veritas compiles them into a specification that every layer of decoding can
read — grammar, interval arithmetic, a small exact solver, and a final concrete evaluator.

It is not a validator you run afterwards. The specification is inside the token loop.

## The problem with valid JSON

A JSON schema can promise that `weights` is an object of numbers. It cannot promise that the numbers
add up to one, that a Sharpe ratio agrees with a covariance matrix, or that a probability distribution
is still a distribution. An LLM will happily produce this:

```json
{
  "weights": { "AAPL": 0.50, "MSFT": 0.45, "NVDA": 0.30 },
  "expected_return": 0.2100,
  "sharpe_ratio": 1.214
}
```

The JSON is valid. The arithmetic is not: the weights sum to **1.25**, and the Sharpe ratio is
inconsistent with the weights. Grammar-constrained decoders accept it. Pydantic raises after you have
paid for every token. Retrying is a gamble with the same odds.

Veritas eliminates the guess. While the model is choosing tokens, a compiled spec:

1. **masks** tokens that would break JSON grammar (Tier 0 — pushdown automaton);
2. **contracts** numeric domains with outward-rounded intervals (Tier 1 — HC4 + affine forms);
3. **splices** derived values instead of sampling them (zero degrees of freedom);
4. **jumps back** with a learned domain cut when a branch is unsatisfiable (CDCL);
5. **verifies** the finished object and can emit an offline certificate.

## A schema that cannot lie

```python
import veritas as vt
from pydantic import BaseModel

class Portfolio(BaseModel):
    weights: dict
    expected_return: float
    volatility: float
    sharpe: float

RETURNS = {"AAPL": 0.14, "MSFT": 0.13, "NVDA": 0.24}
COV = {
    ("AAPL", "AAPL"): 0.048, ("AAPL", "MSFT"): 0.031, ("AAPL", "NVDA"): 0.042,
    ("MSFT", "MSFT"): 0.039, ("MSFT", "NVDA"): 0.036, ("NVDA", "NVDA"): 0.095,
}

@vt.verified_schema()
def portfolio(p: Portfolio):
    vt.require(vt.keys_subset(p.weights, {"AAPL", "MSFT", "NVDA"}))
    vt.require(vt.sum(p.weights.values()) == 1.0, tol=1e-6)
    vt.require(vt.forall(p.weights.values(), lambda w: (0.05 <= w) & (w <= 0.50)))

    vt.derive(p.expected_return == vt.dot(p.weights, RETURNS), tol=1e-5)
    vt.derive(p.volatility == vt.sqrt(vt.quad_form(p.weights, COV)), tol=1e-5)
    vt.derive(p.sharpe == (p.expected_return - 0.04) / p.volatility, tol=1e-5)

report = portfolio.verify({"weights": {"AAPL": 0.40, "MSFT": 0.35, "NVDA": 0.25}})
print(report.status)        # PASS
print(report.values)        # derived fields were filled
```

`@verified_schema` (with or without parentheses) compiles the function body into **VIR**, a typed
intermediate representation with a dependency graph. Compilation also runs **preflight**: if the
constraints contradict each other, construction raises `InfeasibleSpecError` before a model is loaded.

<Callout variant="check" title="The contract">
A generated result is returned only when the final report is `PASS`. `INCOMPLETE` — a missing or
not-yet-evaluable field — is never silently promoted to a pass.
</Callout>

## What makes it different

<FeatureGrid>
  <Feature title="It reasons across fields" icon="layers">
    `sum(weights) == 1`, `dot`, `quad_form`, `sqrt`, `keys_subset` and `forall` are compiled into the
    decode, not checked after it.
  </Feature>
  <Feature title="It computes instead of guessing" icon="zap">
    When a field has zero degrees of freedom, Veritas computes it and splices the bytes in. No forward
    pass, no arithmetic hallucination.
  </Feature>
  <Feature title="It recovers from dead ends" icon="git">
    CDCL jumpback identifies the field responsible for an UNSAT branch, rewinds the stream and stores a
    half-space cut plus a tabu prefix.
  </Feature>
  <Feature title="It proves what it returned" icon="shield">
    Certificates embed the versioned spec, the witness, an SMT-LIB2 rendering and SHA-256 digests for
    offline re-verification.
  </Feature>
  <Feature title="It stays dependency-friendly" icon="cpu">
    The Python engine is the complete product surface. The Rust core is an optional accelerator with no
    external crates and a pure-Python fallback.
  </Feature>
  <Feature title="It knows your domain" icon="database">
    Eight cartridges cover finance, SQL, agent policy, scheduling, statistics, units, SMILES and code
    safety — as composable constraint modules.
  </Feature>
</FeatureGrid>

<TabsContent value="difference">

Grammar tools constrain **syntax**. Pydantic validates **after generation**. Veritas additionally
reasons about cross-field algebra, inequalities and domain invariants **during** generation — and
computes derived fields deterministically, so the model never has to guess arithmetic.

</TabsContent>

<TabsContent value="latency">

No solver runs per token. The JSON pushdown automaton builds an exact mask in **0.23 ms per step**
(native, 605-token vocabulary), interval contraction costs **3.9 µs**, and zero-DoF splicing removes
forward passes rather than adding them. Z3 is optional and never in the token loop.

</TabsContent>

<TabsContent value="syntax">

Zero new languages. If you can write a Pydantic model and Python comparisons, you can write a
specification. SMT-LIB2, Rust and theorem-prover knowledge are not prerequisites.

</TabsContent>

## How the layers fit

| Layer | What it does | Cost |
| :--- | :--- | :--- |
| Preflight | Refutes contradictory specs with interval, container and affine reasoning | 0 tokens |
| Tier 0 · grammar | Exact JSON mask over your vocabulary, pattern NFAs, format witnesses | ~0.23 ms / step |
| Tier 1 · numerics | Outward-rounded HC4 + affine contraction of numeric prefixes and residuals | ~3.9 µs / prefix |
| Tier 2 · search | Deterministic nano-solver, minimal unsat cores, CDCL jumpback, zero-DoF splices | bounded search |
| Verify | Total concrete evaluation, derived fill, PASS / FAIL / INCOMPLETE, certificate | once per object |

Read [How Veritas works](/docs/getting-started/how-veritas-works) for the full walkthrough, or
[Engine internals](/docs/engine-internals/vir-compiler-and-dag) for the mathematics.

## Where it fits

- **Structured generation** — portfolios, invoices, schedules, API payloads, SQL, agent tool calls.
- **High-stakes pipelines** — anything where a numeric inconsistency downstream is expensive.
- **Evaluation and data collection** — every backtrack can become a step-level preference pair for
  DPO / Process-GRPO training.

It is **not** a general-purpose theorem prover, an arbitrary context-free grammar engine, or a
replacement for your integration tests. Grammar support is JSON with a documented schema subset. The
[scope and limitations](/docs/getting-started/troubleshooting) page is explicit about the edges.
